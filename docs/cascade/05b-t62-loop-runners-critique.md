## Brief

| C# | severity | finding | evidence |
|---|---|---|---|
| C1 | medium | The cost model leaves out Gradle's own configuration cache. The cache keeps one entry per distinct command line and reuses it on later passes. So on a build with the cache enabled, "every loop pass repeats that N times" holds only for the first pass. Three costs remain real: the first pass, alternating `--tests` filters that keep a test task from ever being UP-TO-DATE, and the discarded output. The brief and the spec measure only against a baseline with the cache off (28.9s / 29.5s). That leaves two things unproven: how big the win is, and whether a Gradle-specific runner is worth its verdict risk compared with "log every line, document `org.gradle.configuration-cache=true`". | `docs/cascade/05b-briefs.md:119`; the prototype's own single-line command reused its entry: `grep -n -e "Configuration cache entry" -e "Reusing" /tmp/claude-0/-home-user-barbaric-driven-development/bafe8f5e-6213-53e5-b5c7-f46fdcca4393/scratchpad/proto/b3.log /tmp/claude-0/-home-user-barbaric-driven-development/bafe8f5e-6213-53e5-b5c7-f46fdcca4393/scratchpad/proto/b4.log` prints "entry stored" (b3:15), then "Reusing configuration cache" and "entry reused" (b4:2, b4:15) |
| C2 | medium | The brief contradicts itself. It requires that "a faster loop can never report a verdict the sequential loop would not".
