## Spec

| C# | severity | finding | evidence |
|---|---|---|---|
| C3 | high | As specified, the fingerprint rebuild cannot be reached by the case it is meant for. A segment is "the longest run of consecutive taken lines". In t62's model the runner runs the whole segment before `loop.sh` runs any line alone. So "a shell line earlier in the segment" cannot exist. AC2's "shell line between two Xcode lines that edits a source" splits the goal into two one-line segments, and §1 runs one-line segments alone. That AC, AC3's rebuild count and AC3's stale-binary red twin then exercise no batched build at all. | spec `:121-122`, `:130-131`, `:197-200`; `tests/lib/gradle_runner.py:8-10` ("a segment never reaches past a line this file does not take"); `tests/loop.sh` calls `run_segment "$idx"` before the alone `eval` loop |
| C4 | high | Nothing bounds the rebuilds. The after-diagram has the cycle `B --> F`, `F -->\|no\| B` with no exit. The fingerprint covers untracked, non-ignored files. A build phase that writes into the tree (bumping the build number, SwiftLint `--fix`, writing `Package.resolved`) changes the fingerprint on every build, so every line rebuilds. That is worse than today, or an endless loop if implemented as "rebuild until stable". There is no rule to give up and run the lines alone. | spec `:69-71`, `:128-131`; `tests/lib/cascade.sh` `cascade_worktree_sha` ("tracked files and untracked non-ignored ones") |
| C5 | high | Merged mode's real risk is left out. E0 measured pass alone → fail merged, which is harmless because a FAIL always re-runs alone. The dangerous direction is fail alone → pass merged: another class sets static state the test needs, and the result is a false PASS that is never re-checked. That direction is neither named nor tested; AC5 documents only E0's harmless case. §2.3 also requires "every test case that ran is one the line's own selectors select", which merged runs violate by definition. The rule that replaces it for merged proof is never stated. | spec `:36-37`, `:134-137`, `:143-147`, `:203-204` |
| C6 | medium | The plan does not gitignore `.cascade/xcode/<key hash>`, which holds a full DerivedData per build key. `install.sh` writes only `.cascade/loop/`, `.cascade/gradle/` and `.cascade/verdicts/` into `.gitignore`, and neither `install.sh` nor `.gitignore` is in scope. Gigabytes of build products would then show in `git status` and could be committed. The runner also never reuses the user's DerivedData, so its first build is a cold full build; the benefits table leaves that cost out. | `install.sh:179`; `.gitignore` (no `.cascade/xcode/`); spec `:91`, `:128` |
| C7 | medium | There is no Xcode version gate. U4 and Ask 5 say unverified Xcode versions run every line alone, but §1 and §2 never check the version, define no verified range (as `VERIFIED` does in `gradle_runner.py`), and AC1 has no unverified-version case. CI's `macos-latest` Xcode is not pinned to 27.0. If it is outside the range, the stress job could run every line alone and still pass, proving nothing. | spec `:111-118`, `:192-194`, `:270-271`, `:281`; `tests/lib/gradle_runner.py` `VERIFIED = ("8.5", "9.2")` |
| C8 | medium | The timeout does not help in the hang E0 actually saw. That hang came after tests had failed. In the fast path the line is killed after 600s, then re-run alone, where it hangs with no bound (U3). The bound adds up to 600s to a hang it cannot prevent. Whether killing the process group also stops the simulator-side test processes is never checked. | spec `:40`, `:96-97`, `:131-133`, `:268-269` |
| C9 | medium | The CI plan cannot be built as written. `pack-self-check.yml` triggers only on `pull_request` and `push`, with no `schedule` and no `paths`. GitHub Actions has no job-level path filter. Adding `schedule:` to this file would also run `self-check` and the Gradle stress jobs nightly. The stub also has to fake `xcrun xcresulttool`, which the plan's fixture list does not mention. | `.github/workflows/pack-self-check.yml:4-7`; spec `:176-177`, `:188-189`, `:242`, `:266-267` |
